ТЗ по интерфейсу и дизайну
Проект: сервис поиска строительных специалистов

1. Задача дизайнера
Нужно подготовить простой и понятный интерфейс одного сервиса для двух платформ:
веб-сайт на React;
Android-приложение на Flutter.

Оба приложения показывают одни и те же данные:
специалистов;
заказы;
отклики пользователей.

2. Стиль приложения
Интерфейс должен выглядеть современно и аккуратно.
Тема проекта: строительные услуги и поиск исполнителя.

Рекомендуется:
использовать много свободного места;
не перегружать страницы элементами;
делать крупные и понятные кнопки;
использовать одинаковые названия кнопок в web и Android.

3. Цвета
Основные цвета:
оранжевый — кнопки и активные элементы;
белый или почти белый — фон светлой темы;
тёмно-синий — шапка и элементы тёмной темы;
тёмно-серый — фон карточек в тёмной теме;
серый — второстепенный текст и границы.

Примеры кнопок:
“Найти специалиста”;
“Создать заказ”;
“Откликнуться”;
“Войти”.

4. Темы
Обязательно сделать светлую тему.

Тёмная тема является дополнительным заданием. Если команда её делает, цвета и компоненты должны одинаково выглядеть в сайте и Android-приложении.

5. Что нужно нарисовать обязательно
Для сайта и мобильного приложения нужно подготовить макеты:
экран входа;
экран регистрации;
экран дополнительной информации заказчика: тип деятельности, ИНН и подтверждающие документы;
главную страницу;
каталог специалистов;
карточку или страницу специалиста;
каталог заказов;
страницу заказа;
форму создания заказа;
форму отклика;
личный кабинет.

6. Главные компоненты
В макетах должны быть:
кнопка;
поле ввода;
карточка специалиста;
карточка заказа;
фильтр по городу или категории;
сообщение об ошибке;
сообщение “ничего не найдено”;
индикатор загрузки.

Также нужно предусмотреть:
кнопку “Продолжить с Google” на экранах входа и регистрации;
выбор типа заказчика: представитель компании, ИП или самозанятый;
поле ИНН и блок подтверждающих документов для заказчика.

7. Адаптивность
Сайт нужно продумать минимум для двух размеров:
компьютер — ширина около 1440 px;
телефон — ширина около 390 px.

Android-макеты достаточно подготовить для обычного смартфона.

8. Что не обязательно делать
В первой версии не нужны:
сложная анимация;
карта;
оплата;
видеозвонки;
много разных цветов;
отдельный интерфейс компании;
сложная админ-панель.

9. Что сдаёт дизайнер
Дизайнер передаёт:
ссылку на Figma или файл с макетами;
цветовую палитру;
набор основных компонентов;
макеты обязательных экранов;
короткое пояснение, какие состояния есть у кнопок и форм.

10. Критерии оценки дизайна
Проверяется:
понятно ли пользователю, куда нажимать;
одинаково ли оформлены сайт и Android-приложение;
удобно ли читать текст;
есть ли все обязательные экраны;
не ломается ли макет на мобильном размере.


ТЗ на разработку Flutter Android-приложения
Проект: сервис поиска строительных специалистов

1. Что нужно разработать
Нужно создать Android-приложение на Flutter.
Приложение помогает:
заказчику найти специалиста;
заказчику разместить заказ;
специалисту посмотреть заказы;
специалисту отправить отклик.

Важно: сайт и Android-приложение — это один продукт. Они работают с одинаковыми пользователями, специалистами, заказами и откликами.

2. Как устроена командная работа
Android-приложение не создаёт отдельную базу данных.
Оно подключается к общему backend через REST API.

Рекомендуемый порядок работы:
сначала команды согласуют поля данных и адреса API;
web/backend-команда подготавливает Node.js API и PostgreSQL базу;
Android-команда сначала может использовать тестовые данные, затем подключает готовое API.

GitHub для всей команды:
создайте один общий GitHub-репозиторий проекта;
используйте две рабочие ветки: web-backend для сайта, API и базы данных; android для Flutter-приложения;
не создавайте отдельные репозитории для разных платформ;
если меняются сущности или API, команды сначала согласуют изменения и обновляют документацию.

3. Технологии
Обязательно:
Flutter;
Dart;
REST API;
JWT token для авторизованного пользователя.

Можно использовать:
dio или http для запросов;
flutter_secure_storage для хранения токена;
go_router для навигации;
provider или flutter_bloc для состояния.
Google Firebase Authentication для входа через Google.

Важно: Google Firebase используется для авторизации через Google, если команда выбирает этот вариант. Основные сущности проекта, заказы и отклики должны по-прежнему работать через общий Node.js backend и PostgreSQL базу, а не через отдельную мобильную базу.

4. Роли пользователей в MVP
Гость:
смотрит специалистов и заказы;
может перейти к регистрации и входу.

Заказчик:
создаёт заказ;
смотрит специалистов;
смотрит отклики на свой заказ.

Специалист:
создаёт или редактирует анкету;
смотрит заказы;
отправляет отклик.

В MVP не нужны роли компании и администратора в мобильном интерфейсе.

5. Общие данные продукта
Android-приложение должно использовать те же сущности, что и сайт:

User:
id, name, email, passwordHash, role, city, customerType, inn, verificationDocumentUrl, verificationStatus.

Specialist:
id, userId, profession, experience, description, priceFrom.

Order:
id, title, description, budget, city, category, customerId, status.

Response:
id, orderId, specialistId, message, price, status.

6. Экраны, которые обязательны
Нужно реализовать:
экран регистрации;
экран входа;
главную страницу;
каталог специалистов;
профиль специалиста;
каталог заказов;
страницу заказа;
создание заказа для заказчика;
отклик на заказ для специалиста;
профиль текущего пользователя.

Splash screen и onboarding можно добавить, но они не должны занимать время вместо основных функций.

7. Регистрация и вход
При регистрации пользователь выбирает роль:
заказчик;
специалист.

Поля регистрации:
имя;
email;
город;
пароль;
роль.

Если пользователь выбирает роль “Заказчик”, он обязательно указывает, кто он:
представитель компании (ООО, АО/ПАО, ранее ОАО, и другие организационно-правовые формы);
индивидуальный предприниматель (ИП);
самозанятый.

Для заказчика также предусмотреть:
поле ИНН компании или личный ИНН;
загрузку или указание подтверждающих документов;
статус проверки данных: “На проверке”, “Подтверждено”, “Отклонено”.

Перечень требуемых документов и правила обработки персональных данных должны соответствовать действующему законодательству РФ. Для учебной демонстрации используйте только тестовые данные и тестовые файлы, не загружайте реальные документы пользователей.

Поля входа:
email;
пароль.

После входа приложение получает JWT token и сохраняет его на устройстве.

Нужно также добавить регистрацию и вход через Google.
После первого входа через Google новый пользователь всё равно выбирает роль, а заказчик заполняет тип деятельности и ИНН.
Backend должен проверить token Google и выдать JWT token вашего сервиса.
Для реализации Google-входа разрешено использовать Google Firebase Authentication.

8. Каталог специалистов
На экране показать список специалистов.

Карточка специалиста содержит:
имя;
профессию;
город;
опыт;
цену от;
кнопку “Подробнее”.

Достаточно сделать фильтр:
по городу;
или по профессии.

9. Заказы
Заказчик может создать заказ.

Поля заказа:
название;
описание;
категория;
город;
бюджет.

Специалист видит список заказов и открывает страницу выбранного заказа.

10. Отклик
Специалист может откликнуться на заказ.

Поля отклика:
сообщение;
предложенная цена.

Заказчик должен увидеть список откликов у своего заказа.

11. API для приложения
Используется общее API проекта:
POST /api/auth/register
POST /api/auth/login
POST /api/auth/google
GET /api/specialists
GET /api/specialists/:id
POST /api/specialists
PUT /api/specialists/:id
GET /api/orders
GET /api/orders/:id
POST /api/orders
POST /api/responses
GET /api/responses/order/:id

Защищённые запросы должны отправлять JWT token.

12. Обработка ошибок
На экранах нужно показать:
загрузку данных;
ошибку запроса;
пустой список;
ошибку заполнения формы.

Примеры:
“Введите email”;
“Пароль должен быть не короче 6 символов”;
“Заказы не найдены”;
“Не удалось загрузить данные”.

13. Что можно добавить после MVP
Дополнительные баллы можно получить за:
избранных специалистов;
отзывы;
чат;
push-уведомления;
тёмную тему;
загрузку фотографий.

Эти функции делаются только после того, как работают регистрация, заказы и отклики.

14. Что сдаёт Android-разработчик
Нужно передать:
исходный код Flutter-проекта;
APK-файл;
README с инструкцией запуска;
ссылку на общий GitHub-репозиторий и ветку android;
данные тестового заказчика;
данные тестового специалиста;
скриншоты основных экранов.

15. Проверка работы
Приложение считается выполненным, если:
запускается на Android;
можно зарегистрироваться и войти;
заказчик создаёт заказ;
специалист видит заказ;
специалист отправляет отклик;
заказчик видит этот отклик;
данные приходят из общего API;
интерфейс не ломается на экране телефона.


Техническое задание для студентов
Web-приложение на React + Node.js + PostgreSQL
Проект: сервис поиска строительных специалистов

1. Что нужно разработать
Нужно создать веб-приложение, в котором:
заказчик размещает заказ на строительные работы;
специалист создаёт свою анкету;
специалист ищет подходящий заказ;
специалист отправляет отклик;
заказчик смотрит полученные отклики.

Это основная версия общего продукта. Android-приложение подключается к тем же данным через ваше API.

2. Технологии
Frontend:
React + Vite;
React Router;
Axios или fetch.

Backend:
Node.js;
Express.

База данных:
PostgreSQL;
Prisma ORM или другой согласованный способ работы с PostgreSQL.

Авторизация:
JWT token;
пароль нельзя хранить в открытом виде, используйте bcrypt.
регистрация и вход через Google.
Для Google-входа можно использовать Google Firebase Authentication, но бизнес-данные хранятся в PostgreSQL через Node.js backend.

3. Как разделить проект
Проект можно разделить на две папки:
frontend — React-сайт;
backend — Express API и подключение к PostgreSQL.

Пример структуры frontend:
src/
  components/
  pages/
  services/
  App.jsx

Пример структуры backend:
src/
  routes/
  controllers/
  middleware/
  app.js
prisma/
  schema.prisma

4. Роли пользователей в MVP
Гость:
смотрит специалистов и заказы;
может зарегистрироваться и войти.

Заказчик:
создаёт заказ;
смотрит каталог специалистов;
смотрит отклики на свои заказы.

Специалист:
заполняет анкету;
ищет заказы;
отправляет отклики.

Компания и сложная админ-панель не входят в обязательную первую версию.

5. Сущности базы данных
Данные должны совпадать с Android-приложением.

User:
id, name, email, passwordHash, role, city, customerType, inn, verificationDocumentUrl, verificationStatus.

Specialist:
id, userId, profession, experience, description, priceFrom.

Order:
id, title, description, budget, city, category, customerId, status.

Response:
id, orderId, specialistId, message, price, status.

Связи:
один пользователь-специалист имеет одну анкету;
один заказчик может создать много заказов;
один заказ может получить много откликов;
один специалист может отправить отклики на разные заказы.

6. Страницы сайта
Обязательно реализовать:
главную страницу;
страницу регистрации;
страницу входа;
каталог специалистов;
страницу специалиста;
каталог заказов;
страницу заказа;
форму создания заказа;
форму отклика;
личный кабинет пользователя.

7. Регистрация и вход
При регистрации пользователь выбирает роль:
заказчик;
специалист.

Поля регистрации:
имя;
email;
город;
пароль;
роль.

Если пользователь зарегистрирован как заказчик, нужно запросить:
тип заказчика: представитель компании (ООО, АО/ПАО, ранее ОАО, и другие организационно-правовые формы), ИП или самозанятый;
ИНН компании или личный ИНН;
подтверждающие документы;
статус проверки данных: “На проверке”, “Подтверждено”, “Отклонено”.

Перечень документов и порядок их обработки в настоящем сервисе должны соответствовать действующему законодательству РФ. В учебной версии используйте только тестовые реквизиты и тестовые файлы; реальные документы и персональные данные в демонстрационную базу не загружайте.

После входа пользователь получает JWT token.
Страницы создания заказа и отправки отклика должны быть доступны только авторизованным пользователям нужной роли.

Также нужно реализовать регистрацию и вход через Google.
При первом входе через Google пользователь выбирает роль, а заказчик заполняет обязательные данные о типе деятельности и ИНН.
Backend должен проверить token Google и выдать JWT token вашего сервиса.
Для реализации Google-входа разрешено использовать Google Firebase Authentication.

8. Backend и API
Backend принимает запросы от React-сайта и Android-приложения, работает с одной PostgreSQL базой и возвращает JSON.

Обязательные маршруты:
POST /api/auth/register
POST /api/auth/login
POST /api/auth/google
GET /api/specialists
GET /api/specialists/:id
POST /api/specialists
PUT /api/specialists/:id
GET /api/orders
GET /api/orders/:id
POST /api/orders
POST /api/responses
GET /api/responses/order/:id

Нужно проверить права:
только заказчик создаёт заказ;
только специалист создаёт анкету и отклик;
только владелец заказа видит отклики к нему.

9. Минимальный сценарий проверки
Преподаватель должен иметь возможность выполнить шаги:
зарегистрироваться как заказчик;
создать заказ “Ремонт ванной”;
зарегистрироваться как специалист;
создать анкету “Плиточник”;
увидеть заказ в каталоге;
отправить отклик с ценой;
войти как заказчик и увидеть отклик.

Если этот сценарий работает, основа проекта сделана правильно.

аккуратным;

14. Критерии оценки
Проверяется:
работает ли основной сценарий;
правильно ли связаны таблицы базы;
работает ли API для сайта и Android;
защищены ли страницы по ролям;
понятен ли интерфейс;
есть ли инструкция запуска;
использовался ли Git.
создан ли один общий GitHub-репозиторий с ветками web-backend и android.

15. Важное правило для команд
Web- и Android-разработчики делают разные интерфейсы, но один продукт.
Нельзя создавать разные названия ролей, разные поля сущностей или разные правила работы заказов.
Все изменения в API сначала согласуются между командами и записываются в документацию проекта.
У проекта должен быть один GitHub-репозиторий и две рабочие ветки:
web-backend — React-сайт, Node.js API и PostgreSQL;
android — Flutter Android-приложение.

4. ИИ-инструменты, которые можно использовать
ИИ можно использовать для идей интерфейса, объяснения ошибок, создания чернового кода, проверки компонентов и написания README.

Полезные инструменты:
Google Stitch — создание идей и макетов интерфейса: https://stitch.withgoogle.com/
Lovable — прототипирование web-интерфейсов: https://lovable.dev/
Codex — помощь с кодом и проектом: https://openai.com/codex/
ChatGPT — объяснения, идеи и разбор ошибок: https://chatgpt.com/
Claude — объяснения, анализ кода и работа с текстом: https://claude.ai/
Gemini — идеи, объяснения и работа с Google-сервисами: https://gemini.google.com/
GitHub Copilot — подсказки кода в редакторе: https://github.com/features/copilot
Cursor — редактор с ИИ-помощником по проекту: https://cursor.com/
Replit Agent — прототипирование приложений в браузере: https://replit.com/
Bolt.new — быстрые web-прототипы по описанию: https://bolt.new/
v0 — идеи интерфейсов и React-компонентов: https://v0.dev/
Perplexity — поиск информации с источниками: https://www.perplexity.ai/

Важно:
проверяйте и понимайте код, который предлагает ИИ;
не вставляйте в ИИ реальные пароли, токены, ИНН и документы пользователей;
не сдавайте проект, если не можете объяснить, как он работает.
